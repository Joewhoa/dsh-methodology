# 测试驱动开发

TDD 是红 → 绿循环。本 skill 是让这个循环产出值得长期保留的测试的参考指南：什么是好测试、测试应该放在哪里、有哪些反模式，以及循环应遵守哪些规则。每一节都适用于每一次循环；应在循环开始前和进行中查阅，而不是等结束后再看。

探索代码库时，如果存在 `CONTEXT.md`，请先阅读它，使测试名称和接口用语与项目的领域语言一致；同时遵守所修改区域内的架构决策记录（ADR）。

## 什么是好测试

测试应通过公共接口验证行为，而不是验证实现细节。代码可以彻底改变，测试不应因此改变。好测试读起来像规格说明：“用户可以使用有效购物车结账”准确说明了系统具备什么能力；它不关心内部结构，因此能经受重构。

示例见 [tests.md](tests.md)，模拟（mock）准则见 [mocking.md](mocking.md)。

## 接缝：测试放在哪里

**接缝（seam）**是进行测试的公共边界：你可以在此观察行为，而无需伸入系统内部。测试应位于接缝处，绝不针对内部实现。

**只在预先约定的接缝处测试。** 编写任何测试之前，先写明要测试的接缝并与用户确认。不得在未经确认的接缝处编写测试。你无法测试所有内容；预先约定接缝，才能让测试投入集中于关键路径和复杂逻辑，而不是覆盖每个边缘情况。

应询问：“公共接口是什么？我们应该测试哪些接缝？”

如果接口本身的形态仍有疑问，例如模块应有多深、接缝应位于何处或接口应暴露什么，请加载可用的代码库设计 skill 以统一术语。它应作为模块、接口、深度、接缝、适配器、杠杆效应和局部性等概念的参考，而不是另行启动一个会话。如果当前 DSH 会话中没有对应 skill，就依据项目既有设计约定与用户确认结果继续，不要假定不存在的工具。

## 反模式

- **与实现耦合**：模拟内部协作者、测试私有方法，或通过旁路验证结果（例如绕过接口直接查询数据库）。识别信号是：行为没有变化，仅仅重构便会让测试失败。
- **同义反复**：断言以与代码相同的方式重新计算期望值（如 `expect(add(a, b)).toBe(a + b)`、手工按相同过程生成的快照，或断言常量等于自身），导致测试按构造必然通过，永远无法与代码产生分歧。期望值必须来自独立的事实来源，例如已知正确的字面量、推演完成的示例或规格。
- **水平切片**：先写完所有测试，再写所有实现。批量测试验证的是**想象出来的**行为：测试的是事物的**形状**而非用户可见行为；测试对真实变化变得不敏感；在理解实现之前便锁定了测试结构。应改用**垂直切片**：一个测试 → 一个实现 → 重复。每个测试都是一枚**曳光弹（tracer bullet）**，根据上一轮循环所得的认识作出响应。

## 循环规则

- **先红后绿。** 先写一个会失败的测试，再只写足以让它通过的代码。不要预判未来测试，也不要添加推测性的功能。
- **每次只做一个切片。** 每轮只处理一个接缝、一个测试和一个最小实现。
- **重构不属于这个循环。** 它属于评审阶段，而不是红 → 绿实现循环；评审时使用当前 DSH 环境可用的代码评审流程。
